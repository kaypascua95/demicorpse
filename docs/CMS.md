# Owner-only publishing

## Architecture decision

The existing repository is a React/Vite SPA with Netlify hosting, a persistent video
element and custom history navigation. Moving hosting or rebuilding the frontend
would be unnecessary. Supabase is used only for Auth, PostgreSQL, and private Storage.

Base44 was evaluated first. Its external SDK supports this frontend, so this is not
a claim that Base44 is categorically incompatible. However, this session could not
verify the complete combination of closed registration, per-owner upload permissions,
and publication-dependent private-media access through its available controls. Its
CLI provisioning was also blocked by a remote dependency restriction. The selected
fallback offers explicit, versioned and executable database/storage policies and
keeps the current frontend and hosting intact.

References: [Base44 external client](https://docs.base44.com/sdk-getting-started/client),
[Base44 login and registration](https://docs.base44.com/Setting-up-your-app/Managing-login-and-registration),
[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security),
[Storage permissions](https://supabase.com/docs/guides/storage/security/access-control).

- Public signup and anonymous sign-in must remain disabled under Authentication →
  Sign In / Providers. Only email/password login is needed.
- Owner binding is a single row in `private.cms_owner`, set administratively after
  creating the intended Auth user. An empty row set denies all publishing.

To set or replace the owner, use the SQL editor as project administrator, substituting
the verified Auth user UUID (not an email, role or editable profile field):

```sql
insert into private.cms_owner(singleton, user_id)
values (true, 'YOUR-AUTH-USER-UUID'::uuid)
on conflict (singleton) do update set user_id = excluded.user_id;
```

There is deliberately no first-user-wins flow, signup page, API owner setter, or
editable admin flag. A user with a valid login but a different UUID gets no write or
draft-read access. Keep the Supabase organization/dashboard account secure as it
controls the database; project administrators inherently retain infrastructure access.

## Data model

`cms_entries` uses a constrained `collection` value for JournalEntry, Fragment,
PlayEntry and ArchiveItem. Shared authorization/publication logic is atomic, and fields
remain explicit: title, slug, excerpt, content, cover_image, published_at, status,
tags, created_at, updated_at, date, game, type, description, media. Slugs are unique
within each collection. Timestamps are set by triggers. Media paths must belong to
the same entry, preventing a published post from referencing another entry's draft files.

## Security boundary

- Anonymous requests can SELECT published rows only; no write grants.
- Authenticated non-owners can SELECT published rows only; RLS rejects mutations.
- The single owner must complete authenticator MFA (JWT `aal2`) to read drafts,
  create/edit/delete entries, or upload/delete files. Password-only owner sessions
  have the same content/media access as public readers, even before MFA enrollment.
- The owner lookup uses a fixed-search-path SECURITY DEFINER function in a private
  schema. Its public RPC wrapper is SECURITY INVOKER and returns only the caller's
  authorization boolean. The separate `cms_is_owner_account` RPC identifies the
  caller for MFA onboarding only; no data policy uses it. No API role can read or
  modify the owner table.
- `cms-media` is private, limits accepted MIME types and file size, and has its own
  RLS. It serves only files referenced by currently published rows, or to the owner.
  No permanent public URLs or signed URLs are generated by the app. Downloads use
  the current request's RLS and render through revocable in-memory blob URLs.
- Upload paths are random and immutable; no Storage UPDATE policy exists.
- Unpublishing blocks new anonymous fetches. Content already downloaded, copied, or
  retained in an open page cannot be recalled. Reload a public page to get current status.
- Deletion first unpublishes, then removes files, then deletes the row. Failures leave
  a private draft that can be reopened/retried. A failed upload-link save attempts to
  remove its orphan; the entry's Delete action also lists/removes unattached files.
- Saving uses `updated_at` optimistic concurrency to reject stale edits.
- Raw Markdown HTML and inline remote images are not rendered; links use safe protocols.
- Auth tokens use tab-scoped sessionStorage. Only public project configuration ships
  in JavaScript. There is no service-role key or password in source/build/config.

## Deployment and recovery

Netlify's existing `main` branch workflow and SPA rewrite remain. The two public
environment values are in `netlify.toml`; use the same names in `.env.local` for local
work. A one-time code deployment installs the CMS. Subsequent content changes are live
database operations. To move projects, apply migrations, disable signups, create/bind
the owner, update the two public variables, then deploy once.

To recover a password, use the Supabase dashboard's user management/password recovery
flow with a supported redirect, or administratively create a replacement Auth account
and rebind ownership. The UI intentionally has no public registration or account
creation endpoint. Configure custom SMTP and a recovery flow before enabling any
self-service reset emails; the current CMS uses direct password login only.

## Verification

`npm test` runs PostgreSQL grants/RLS/trigger tests against every collection, both
anonymous and non-owner authenticated roles, draft visibility, media references,
publication transitions, immutable identity, and deletes. `npm run test:e2e` tests
desktop/mobile routing, entrance/logo, persistent video DOM, Markdown safety,
non-owner denial, editor CRUD, uploads, preview and publication using simulated APIs.
These tests do not substitute for hosted Auth or Storage service tests. Production
read/write denials, closed signup settings, and Supabase security advisors are checked
separately during setup. No real user writing is used as test content.


## Authenticator MFA and browser policy

On your next visit to `/admin`, sign in and choose **Set up authenticator**. Scan
its QR code in an authenticator app, keep a secure app backup, and submit the
six-digit code. Later sign-ins request an authenticator code. Enrollment secrets
exist only in component memory and are never written to logs, storage or the repo.
Abandoned unverified enrollments are cleaned up on retry; verified factors are never
removed by the application. Multiple verified authenticators can be selected at login.

MFA is mandatory in PostgreSQL, including Storage policies, rather than just an
editor screen. Do not change that check to allow `aal1` during recovery. If the
owner loses every authenticator, a trusted Supabase project administrator must use
Auth user management to remove the lost factors and revoke sessions, then let the
owner enroll again. Existing access tokens can survive sign-out until expiry; use
an administrative owner-binding removal when immediate CMS access revocation is
needed. Secure the Supabase dashboard account independently with MFA.

Netlify sends an enforced Content Security Policy on all routes: scripts must be
same-origin, inline scripts/event handlers and eval are blocked, connections are
limited to this site and the dedicated Supabase project, and embedding/base URL
changes are forbidden. Images support local files, private-media blobs and the MFA
QR data URL; fonts allow Google Fonts. Inline **styles** remain allowed because the
existing cinematic animations use them. This does not allow inline scripts.

Leaked-password protection remains unavailable on this project's Free plan.
Supabase requires Pro or above. After an owner-authorized upgrade, enable
Authentication > Sign In / Providers > Email > Prevent use of leaked passwords.
It checks new/changed passwords and does not retroactively certify the existing
password. No paid upgrade was performed for this change.
[Supabase password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

Tests now include password-only and missing-assurance denials, MFA onboarding,
incorrect codes, verified login, and CSP script/connection blocking, with existing
CRUD, media, and navigation cases running under the production policy on desktop
and mobile. Auth browser responses are fixtures; owner enrollment in the live
service must be completed privately by the owner.
